## 一、业务题（10 题）

### B1. 这个系统防代签的核心思路是什么？为什么取消了二维码？取消之后靠什么兜底？

**考察点**：对产品本质的理解，能否说清「凭证 vs 生物特征」的区别。

**参考答案**：
防代签的核心是把「人在现场」的证明从**凭证**（二维码、口令，本质是「只要知道就能签」）转移到**生物特征 + 行为**（人脸 1:N 比对 + 指定动作活体 + 首末帧一致性）。凭证可复制转发，生物特征不可转移。

取消二维码（CR-013）的理由是分析它的两个职责：
1. 传递 sessionId 给学生手机——登录体系完备后已无必要，学生首页直接出现进行中的场次；
2. 证明人在现场——本来就不可靠，二维码可拍照外传，15 秒轮换只提高转发成本，不改变性质。

取消后新增的风险是「知道 sessionId 就能换票」，补偿控制三条：
- `join` 强制校验人脸档案 `ACTIVE`，没有档案连票都拿不到；
- checkinTicket 60 秒有效期、一次一用（绑定 sessionId + studentId + ticketJti）；
- 三道活体/一致性/动作门禁 AND，全部通过才落考勤。

**追问防线**：「那有人拿高清照片/视频翻拍怎么办？」——预录视频走三道门禁：单帧活体中位数、首末帧向量余弦、动作连续段；照片翻拍另有伪装识别（口罩/墨镜/帽子）与被动活体特征（占位，真机标定前不开闸）。

### B2. 签到会话为什么要在创建时固化「应到名单快照」（session_expected），而不是每次实时查班级学生表？

**考察点**：对「事实快照」与「实时视图」的取舍，审计意识。

**参考答案**：
三个理由：
1. **历史不可篡改**。点名是对「某时刻谁应该在场」这一事实的记录。如果实时查 class_id，学生事后转班，历史应到人数会被改写，导致已生成的考勤记录与名单对不上——审计口径就崩了。
2. **一致性**。开场瞬间名单定格，运行期间的学生增删、班级调整不影响本场统计，避免「签到了但名单里没他」这类边界纠纷。
3. **性能**。5000 人大班开场时名单已就绪（实测开场 46ms），签到高峰不需要每帧反查学生表。

对应设计：CR-001 应到名单快照；查询「谁没来」以 session_expected 做 LEFT JOIN，而不是以班级名册为基准。

### B3. 活体检测为什么用三道门禁 AND，而不是把活体分、动作分加权平均出一个综合分过阈值？

**考察点**：对防攻击体系设计的理解，能否说清加权平均的结构性漏洞。

**参考答案**：
三道门禁是：① 单帧活体分（多帧取中位数）≥0.55；② 首帧 vs 末帧向量余弦 ≥0.55（拦中途换人）；③ 动作连续段计数达标。

拒绝加权平均的原因是它的结构性漏洞：加权允许「一个强信号掩盖一个弱信号」。预录视频的活体分可能只有 0.1，但播放的动作完全达标为 1.0，`0.5×0.1 + 0.5×1.0 = 0.55` 恰好过线——而这正是要拦的攻击。AND 门禁要求每道独立达标，堵死单点突破。

另一个细节：多帧活体分取**中位数**而非均值/最大值——均值会被少数离群帧拉偏，最大值等于给攻击者「多试几次总有一次过」的机会。

再一个细节：动作判定统计**连续段**而非达标帧总数。真动作一定落在连续时间段里；对齐误差、JPEG 压缩噪声是零散单帧尖刺，早期版本统计总数时一张平移 6px 的照片就能凑够帧数。

### B4. 动作库为什么只有 5 个动作？「眨眼」为什么改成了「闭眼保持 1 秒」？张嘴为什么永久停用？

**考察点**：动作准入标准（量化分离度）、采样定理、产品与安全平衡。

**参考答案**：
**准入标准**：任何动作上线前必须用探针脚本量出两个数——真人做动作的指标均值、静止+抖动+压缩噪声下的标准差，分离度 < 3σ 不得上线。实测：靠近/离远 13.7σ、转头 11.5σ、闭眼 3.9σ（够用但偏紧，附加基线门槛剔除低对比样本）。禁止凭直觉选动作，否则学生站在摄像头前反复失败且原因无从解释。

**眨眼改闭眼**：这是采样定理问题，不是调参问题。自然眨眼 100~300ms，前端 250ms/帧采样，多数眨眼完整落在两帧之间；再叠加「连续 ≥2 帧达标」，真人做对也判不过。采样率低于信号奈奎斯特要求，调阈值永远调不出来。改成「闭眼保持约 1 秒」把事件型动作变成持续型，同一套眼区暗度判据，不再赌采样运气。

**张嘴停用（CR-018）**：产品决定——不要求学生当众张嘴。判据与阈值保留供回滚（改 FA_ACTION_WHITELIST + 重建容器）。

**加分项**：判据信号选择有两条硬约束——关键点只用于定位 ROI 与活体，判动作用「ROI 内亮度统计」或「检测框尺度」，避开形状归一化误差（曾用关键点开合比判张嘴，真人嘴部纵向拉伸 35% 指标只变 1%，换暗度统计后分离度提升 17 倍）；ROI 尺寸在基线帧定一次之后刚性跟随，基线必须取自指令出现之前。

### B5. 学生刷脸失败怎么救济？申诉机制怎么设计的？为什么签到进行中就允许申诉，还要和签到互斥？

**考察点**：业务闭环意识、状态机设计、并发冲突处理。

**参考答案**：
申诉状态机：`PENDING → APPROVED / REJECTED / WITHDRAWN`。学生可在失败页和采集页常驻入口发起申诉，教师/管理员裁定，通过后补记考勤。

**签到中可申诉（CR-015）**的理由：如果不允许，学生只能等会话关闭，救济周期拉长。但允许后产生一个并发冲突：同一场次「申诉未决 + 又去签到」会让考勤状态产生两个争议来源（签到成功与申诉通过撞车）。

互斥设计：同场存在 PENDING 申诉时，`join` 和 `commit` 都返回 `FA-5001`；首页标「申诉中」并阻止进采集页。即「申诉优先、单通道裁定」，同一学生在同一场次要么走签到、要么走申诉，不能同时进行。

### B6. 考勤导出 Excel 为什么只有 8 列，不放相似度分、活体分？这是业务考量还是技术偷懒？

**考察点**：对「内部排障数据」与「业务交付物」的边界意识。

**参考答案**：
是明确的业务决策（业主拍板），不是偷懒。相似度/活体/身份分值是**排障与申诉裁定的内部依据**，不是业务字段。放进教师手里的表，就会被当成「按概率判定签到是否有效」的依据——现场确实出现过教师拿 0.63 的相似度质问「为什么这也算签到成功」。

问题在于：阈值判定是「过线即通过」，0.55 过线和 0.9 过线业务上完全等价；把连续分值暴露给非技术角色，必然引发对 borderline case 的无限争论，而学生个人相似度还涉及生物特征信息泄露（最小必要原则）。

申诉裁定需要这些分值时，走管理端会话详情的门禁明细（CR-007），有权限控制，不随导出扩散。

### B7. 教师权限怎么设计的？「班级负责教师」「开课教师」「授权学生」三件事为什么这么拆？

**考察点**：授权模型的粒度与方向性。

**参考答案**：
三层模型：
1. **班级负责教师**：纯标注字段（类的归属），不产生任何操作权限；
2. **开课教师（owner）= 授权入口（CR-027）**：管理员建课/改课时幂等写入 `teacher_scope(COURSE)`，教师对课程的一切操作以授权表为准；幽灵教师写 owner 直接拒绝（FA-2001）；
3. **课程授权学生（CR-026）**：`course_student_grant` 是授权表不是选课表，应到名单在快照生成时 UNION 追加，解决跨班选修、转班补授的散生点名问题；只影响新会话，不改历史。

**方向性**是关键细节：管理员改 owner 才产生授权（权限从管理员流向下）；TEACHER 建课 owner 强制本人（建课即自见），改课 owner 仅作归属标注、不产生新授权——防止教师「把课转给别的老师」变成给自己扩权。撤旧授权走单独的授权范围抽屉，改 owner 不自动撤，避免误伤。

**追问防线**：「为什么不建选课表？」——现有业务没有整班选课场景，班级与课程保持互不引用（松耦合），授权表按需补充点名口径，模型更简单。

### B8. Agent 智能助手怎么防止「模型一句 hallucination 就把别人的课关了」？分级和确认怎么设计？

**考察点**：LLM 应用的安全边界设计。

**参考答案**：
L0~L3 能力分级：L0 只读查询、L1 生成草稿（不落库）、L2 写操作（必须确认）、L3 定时批量（确认 + 管理员授权，默认关）。

写操作五道闸，缺一不可：
1. **授权**：Java 侧校验角色 + teacher_scope，Agent 无自行扩权可能；
2. **预览**：影响条数、字段级 diff、可撤销截止时间；
3. **确认**：LangGraph `interrupt()` 挂起，UI 渲染确认卡，用户显式点击——「要不要确认」绝不交给模型判断；
4. **令牌**：60 秒一次性 confirmToken，**绑定 paramsHash**，防「确认了 A、执行了 B」；
5. **留痕**：agent_action_log 记 before/after，30 分钟内可 undo。

**不给裸 SQL 工具**：所有查询走预定义语义接口，天然免疫注入与越权扫描；工具目录由 Java 下发，Agent 无法自行注册工具；返回 DTO 在类型层面就没有图片与向量字段，杜绝生物特征数据进模型上下文。

**模糊匹配反问**：「张三」命中 2 人时不许猜——猜错就是给别的班发签到。查不到就说「未存在」，不编造。

**加分项**：确定性规则跑在模型之前时，规则的正则就是系统能力边界——曾出现「导出近两天考勤」被姓名正则截出 `studentName=出近两天`，修复是导出意图前置 + 非人名词护栏 + 统一相对时间解析。

### B9. 人脸数据的隐私合规是怎么处理的？为什么「勾选框」被废除，改成弹窗 + 服务端强校验？

**考察点**：PIPL 敏感个人信息要求、合规与工程实现的映射。

**参考答案**：
《个人信息保护法》把生物识别列为敏感个人信息，要求**单独同意、最小必要、可删除、有期限**。四条对应的工程实现：

1. **单独同意**：勾选框废除，因为「默认勾选 + 与协议捆绑」不构成单独同意。改为进入采集页即展示《告知 v2》全文弹窗（点遮罩不关闭），点「同意并开始采集」→ 调 `POST /mobile/face/consent` → 成功后才启动摄像头。同意落 `face_consent_record` **事件表（只增不改）**，`enroll` 服务端强校验当前版本 ACCEPT 事件，缺失即 `FA-4010`——前端弹窗只是交互，**强制力在服务端校验**。
2. **可删除**：`POST /mobile/face/data-deletion` 自助一键物理删除向量与档案并撤回同意，免审批；归档学生同步清脸；历史考勤不随人脸删除（考勤是业务事实，不是生物特征）。
3. **有期限**：审计日志 365 天、Agent 留痕 180 天由 LogRetentionJob 自动清理，样本缓存 Redis TTL 15 分钟。
4. **最小必要**：人脸原图不落盘，内存处理完即丢弃，只存 AES-256-GCM 加密向量。

**加分项**：同意记录设计成事件表而非状态位的理由——同意本身是「某时刻某人同意某版本告知书」的法律事实，需要可追溯、可举证，只增不改才符合审计要求。

### B10. 学生刷脸失败有重试上限，这个上限为什么要做「四处齐」？漏一处会发生什么？

**考察点**：防绕过意识——安全计数必须收敛到单一权威源。

**参考答案**：
失败上限默认 3 次（`app.checkin.max-retry`），计数落独立的 `checkin_attempt` 表，**只增不减**。为什么四处：签到链路上失败的入口不止一个——
1. Java `join`（拿票前）；
2. Python `start`（建挑战前）；
3. 会话数据 `active.retryLeft`（采集页展示）；
4. `finish` / `frame` 中止上报（rejectGate=commit 不计）。

任何一处漏判，学生换一个入口就能重置次数绕过锁死。所以四个入口读同一个权威源（checkin_attempt 表），而不是各自维护内存计数。

**为什么只增不减**：计数如果可以因成功或超时清零，攻击者可以触发清零后无限重试；「只增不减 + 上限锁死」语义简单、无法绕过。重试上限与票据 60 秒、挑战 TTL 组合，把暴力尝试的速率压到无意义。

## 二、技术题（10 题）

### T1. 为什么人脸推理放服务端而不是浏览器端？为什么帧直连 Python、落库却归 Java？这两个决策分别换来了什么？

**考察点**：D1 + D2，端云分工与信任边界。

**参考答案**：
**D1 推理放服务端**：手机只做 getUserMedia 抓帧（约 4fps、480p JPEG）上传。放弃 onnxruntime-web 端侧推理的三个理由：① WASM 相比原生推理降速约 5 倍，中低端手机撑不起逐帧判定；② 多帧时序判定（动作连续段、基线对比）需要跨帧状态，端上做等于把防伪逻辑暴露在客户端，可被篡改；③ 服务端可集中升级模型，不依赖用户更新页面。

**D2 帧直连 Python、写库归 Java**：每人每次 3~8 帧，若经 Java 中转会多一跳并让 Java 承担图片 IO。但「考勤记录」必须**单一写入口**才能保证审计与事务一致。所以 Python 判定通过后调 Java 内部接口 `POST /internal/checkin/commit` 落库，配合 Redis SETNX 保证只提交一次。

关键点：这不是性能优化，是**信任边界**——Python 手里只有 Java 签发的 60 秒票据，无法自行伪造考勤。即使 Python 服务被攻破，攻击面也只是「看帧」，不是「写考勤」。

### T2. 512 维人脸向量为什么存 MySQL BLOB + 应用层暴力点积，而不上 FAISS/Milvus？什么信号出现时才该换？

**考察点**：D3，技术选型的量化依据与演进触发条件。

**参考答案**：
选型逻辑：512 维 float32 小端序 BLOB，启动时全量载入 numpy 矩阵，余弦相似度即一次点积。规模估算：5000 学生 × 5~10 条向量 ≈ 5 万条 × 512 维 ≈ 100MB 级矩阵，全量驻留内存毫无压力，暴力点积毫秒级完成。

**压测验证**：向量从 1086 → 6171（5.7 倍）时，串行签到耗时 154.3s → 148.2s（-4%，属运行抖动），search_top2 稳定 1~3ms。结论：**1 万人规模内不需要 ANN**。瓶颈根本不在检索，在 FACE_WORKERS=2 的推理并发（可用并发≈14 条签到流水，c30 时每帧 8.55s 会击穿挑战 TTL）。

演进触发条件写死在方案里：向量超 10 万条或单机内存放不下时替换——匹配逻辑封装在 `domain/match` 内，接口不变，换 FAISS 不影响其他模块。提前上向量库的代价是：多一个常驻组件、多一份向量副本的一致性问题（我们已经有「全量快照 + 10s 轮询」的同步机制，向量库只会放大它）。

### T3. 讲一个你印象最深的 bug：真机口罩检测 100% 误报，测试素材却全过——怎么定位、根因是什么、沉淀了什么？

**考察点**：4.1 事故复盘能力（这是本项目最典型的案例，几乎必问）。

**参考答案**：
**症状**：伪装识别（CR-025）上线后真机签到全量报 FA-4009「请摘除面部遮挡物」，所有人都是干净脸；CASIA 合成素材上 40/40 通过。

**定位**：不猜代码，先取证——加 `diagnose()` 打点回传每帧 Cr/Cb 实测值。真机肤色 Cr≈156、Cb≈105，两个值**同时落在判定区间外**。

**根因**：`cv2.COLOR_BGR2YCrCb` 的输出通道顺序是 `[Y, Cr, Cb]`，即 idx1=Cr、idx2=Cb。原实现把肤色区间 Cr∈[125,180] 挂在了 idx2、Cb∈[70,135] 挂在 idx1——**双通道挂反**。

**为什么标定没发现**：CASIA 素材饱和度低，Cr/Cb 都贴着 128 徘徊。挂反后两个判据互相「补偿」，在标定集上自洽。只有真实肤色（高饱和、Cr 明显偏高）才暴露。教训是：**错误与错误可以互相印证，测试集分布决定错误能否幸存**。

**沉淀**：
- 任何新写 YCrCb 代码，先用纯红/纯蓝像素跑实证（纯红 idx1=255、纯蓝 idx2=255），两行断言即可证伪通道顺序；
- 保留已知盲区清单：中性灰白织物（Cr/Cb≈128/128）落在肤色区间内，判据天然失效，由匹配门禁兜底；
- diagnose() + DISGUISE_DUMP_DIR 落盘开关（默认关）留作现场取证。

### T4. 「眨眼动作真人做也过不了」——为什么调阈值调不出来？你们怎么从根上解决？这暴露了验收的什么漏洞？

**考察点**：4.3，采样定理 + 「判据灵敏度 ≠ 时序可达性」的方法论。

**参考答案**：
**根因**：自然眨眼 100~300ms，前端固定 250ms/帧采集，多数眨眼完整落在两帧之间；再叠加连续 ≥2 帧达标的要求，真人做对也判不过。这是采样率低于信号奈奎斯特要求的必然结果——**调阈值是在错误的信号上优化，永远调不出来**。

**修复**：动作语义改为「闭眼保持约 1 秒」（EYE_CLOSE），把事件型动作变持续型，同一套眼区暗度判据，不再赌采样运气。

**深层问题（hold 帧数的二次修正）**：CR-021 初版 hold=2，理论上 1 秒闭眼应落 4 帧。但真机实测：250ms 定时 + 串行上传队列 + 服务端单帧 det 460ms + ArcFace 260ms ≈ 800ms，**有效入库帧率只有 ~1.25fps**——1 秒闭眼只落 1~2 帧，转头「保持半秒」常态 0 帧。E2E 当时全绿，因为合成序列是同步逐帧 POST（4 帧全到），**掩盖了时序稀疏**。

**沉淀**：探针量出的 3.9σ 是「判据灵敏度」，不是「时序可达性」，两者必须分开验收。合成帧序列只能证明「指标能区分状态」，不能证明「真人在采样约束下做得到」。后续把 det 640→320 + 隔帧 ArcFace 把单帧压到 ~300ms，消化率回到 ~3fps，hold 恢复为 2。

### T5. 压测时偶发「模型加载成功但识别全失败」，重启才恢复，无法稳定复现——根因是什么？

**考察点**：4.4，并发初始化的经典陷阱。

**参考答案**：
**根因**：引擎 `load_all()` 无锁，压测多线程并发首次进入时，各线程各自构建 registry 并互相覆盖，其中一个线程可能拿到 None；更糟的是加载中途失败时 `_registry` 被赋成半成品，**此后永久半赋值**——因为判断条件只检查「是否已加载」，不检查「是否完整」。失败会重试，半成品会被当成完成态，所以「重启即恢复、之后必现」。

**修复**：双检锁 + **加载全部成功后才整体赋给全局**——构建到局部变量，最后原子替换。半成品永远不出现在共享状态里。`VectorIndex` 全量矩阵加载同样处理。

**沉淀**：模型/索引类单例的初始化，「部分成功」比「完全失败」更危险。判断共享状态是否就绪时，必须连同「完整性」一起判断，或者干脆让不完整的状态根本不可见（原子替换）。

### T6. 管理员界面右上角显示管理员，接口却报 FA-1003 无权限，退出重登才好——怎么分析和修复？

**考察点**：4.5，令牌快照与数据一致性的经典问题。

**参考答案**：
**分析**：界面身份来自 `/auth/me`（读库），写接口鉴权读 JWT 里的 `role`（签发时快照，有效期 30 分钟）。角色变更后两者不同步——用户看到「界面管理员、接口无权限」。同一机制还有反向风险：停用教师后旧令牌仍能用 30 分钟。

**修复**：鉴权改为**以库中角色为准**——`AccountRoleResolver` 带 30 秒 TTL 缓存 + 写路径主动失效。令牌只证明「你是谁」（身份与签名），角色与账号状态每次向库要。两个效果：不一致窗口从 30 分钟压到 30 秒内；角色变更即时生效。

**容易漏的细节**：缓存的 invalidate 必须在**事务提交后**（afterCompletion）执行。如果在事务内失效，并发读会把未提交的旧角色重新灌进缓存，等于没失效。

**前端配套三层**：捕获 FA-1003 先复核 /auth/me 给出可行动文案（报「当前账号（姓名/角色）没有该权限」而不是裸 403）；监听 storage 事件处理多标签页换账号；路由守卫同步纠正。

### T7. WebSocket 实时大屏一直 401 连不上，前端只显示「等待签到」——根因和修法？为什么说「放行握手 + 帧层校验」是唯一可行解？

**考察点**：4.7，浏览器约束下的 WS 鉴权两阶段设计。

**参考答案**：
**根因**：SecurityConfig 用 `authenticated()` 拦截 `/live`，但浏览器 `WebSocket` 构造函数**无法设置自定义请求头**，JWT 只能走 query 参数——契约本来就是这么设计的，安全配置却按普通 HTTP 接口写了，握手直接 401。

**修复**：握手路径放行，鉴权后置到握手完成后的 `LiveWsConfig.authorized()`——验签 + 角色 + 黑名单，非法连接由服务端主动断开。

**为什么是唯一可行解**：WS 鉴权发生在两个阶段（握手 HTTP 请求 / 帧通道）。握手阶段浏览器无法带 Authorization 头；而帧通道的鉴权必须在连接建立后做。所以「放行握手 + 帧层校验 + 非法连接服务端断开」是浏览器约束下仅有的干净方案。额外的注意点：JWT 走 query 参数会进访问日志，token 应短时效且专用。

**验证细节**：`curl` 测不了 101 协议升级，验收时用标准库 socket 手搓 WS 握手，专门断言「坏 token 握手放行后服务端主动断开」这条语义。

### T8. 教师/管理员改密码后，旧令牌为什么能立即失效？为什么不用 Redis 黑名单？

**考察点**：CR-022，无状态令牌的吊销方案对比。

**参考答案**：
用 **credential_version** 方案：密码/登录名变更成功后 `credential_version + 1`，该值写入 JWT 的 cv claim；鉴权时比对新旧 cv，不一致即 401。

**不用 Redis 黑名单的理由**：
1. 黑名单要枚举旧令牌（jti）列表，而「改密前签发的所有令牌」数量不定、TTL 内都活着，逐个吊销易漏；
2. 引入强依赖：Redis 不可用时鉴权降级路径复杂（放行有洞、拒绝误伤）；
3. cv 方案是 O(1) 比较，一次字段比对覆盖「该用户此前所有令牌」，天然完备。

**配套细节**：BCrypt 在提交时计算并暂存（明文只存在于那一次请求，hash 暂存待审核）；通过/驳回/撤回都清暂存；管理员可带 password 直接重置兜底。改密申请链（CR-024）同样靠暂存 hash + 审核状态机。

**追问防线**：「为什么不干脆缩短 JWT 有效期？」——短有效期缓解但不解决（窗口内仍有效），且把续期压力转嫁给客户端；cv 是精确吊销。

### T9. 「清空教师院系」保存成功但值没变——这个 bug 牵出了哪三层失真？最终契约怎么定的？

**考察点**：4.6，REST + ORM 组合下「部分更新」语义的端到端定义。

**参考答案**：
**三层失真**：
1. **前端层**：清空时发 `null`，后端把 `null` 解释为「该字段不改」——JSON 无法区分「没传」与「传 null」；
2. **ORM 层**：MyBatis-Plus `updateById` 默认跳过 null 字段，即使前端改发空串，也不会生成 `SET col = NULL`——「清空」永远不落库；
3. **语义层**：「没传」「传 null」「传空串」三种客户端表达被压到两个后端语义里，必然丢一种。

**最终契约**（端到端定义一次，写进文档）：`department`/`title` **传空串 = 清空，不传/null = 不改**；持久层新增 `updateDepartment/updateTitle` 显式 `SET col = NULL`，管理员编辑与教师申请审核两条路径共用，不允许再走 updateById。

**沉淀**：部分更新语义在 REST + ORM 组合下会三次失真，必须端到端定义并写进契约，不能靠约定俗成。类似坑还有「PENDING 唯一性用生成列约束」绕开「多行 NULL 不冲突」的数据库默认行为。

### T10. 1:N 匹配为什么要 top1 − top2 ≥ margin？同一张脸录进两个学号时会发生什么？为什么查重要前置到写入路径？

**考察点**：4.9，margin 判据的失效模式 + 数据质量前置。

**参考答案**：
**为什么 margin**：1:N 用「top1 − top2 ≥ 0.06」判定，本质是要求「最像的人明显比第二像的人更像」，防止库里有长相极近的两人时 top1 撞到别人。

**同脸双档的失效模式**：学号 57 与 158 录了同一张脸（向量相似度 0.692），签到时 top1、top2 都是他自己，差值≈0，margin < 0.06 → 本人被判 FA-4005「比对不通过」。规则把「本人」误判成「两个长得很像的人」——触发的是防混淆分支，报错完全反直觉。压测时把同一向量复制给多学生同样复现全员 FA-4005。

**为什么查重前置（CR-014）**：margin 判据的失效模式是「相似度整体抬高」，它**不区分攻击与脏数据**，指望匹配层兜底会让脏数据以难归因的方式爆发。所以建档时把新样本与全库他人档案逐一比对，任一样本余弦 ≥0.55 即整单拒绝（FA-4008），不写向量、不改状态——从写入路径堵死。

**匹配层的工程处理**：top2 计算先按 studentId 聚合取 max 再比 margin（同一学生的多条向量不互相挤压 margin）。

**沉淀**：margin 类判据的错误信号是「相似度普遍偏高」，归因时**先查数据再查算法**——数据脏了，算法怎么调都是错的。
