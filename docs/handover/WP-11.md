## 2. §7.4.1 六类真机问题逐条落地

| # | 要求 | 代码位置 | 实现方式 |
|---|---|---|---|
| 1 | 设备枚举必须在开流之前 | `useCamera.refreshDevices()` | 函数开头 `if (stream.value) return devices.value` —— **有流时直接返回缓存，绝不再枚举**；首次无 label 时用「临时开流→立刻 stop→再枚举」的解锁动作，整段也发生在真正开流之前 |
| 2 | 流断了要直接重连，不能靠亮度判断 | `startWatchdog()` | 先判 `track.readyState !== 'live' \|\| videoWidth === 0` → 立即 `close()+open()`；亮度只在**流仍然活着**时才用于「画面全黑」判断 |
| 3 | 连续 3 帧取不到才提示；连续 8 帧且流仍在 → 重连，最多 2 次 | `startWatchdog()` 的 `blankStreak` / `RECONNECT_AFTER_BLANK=8` / `MAX_RECONNECT=2` | 单帧失败不提示；超 2 次转 `ERROR` 并提示「刷新页面」 |
| 4 | 探测帧与校验帧必须同参数 | `CAPTURE` 常量 + 唯一入口 `captureSmall()` | 只有一个 `{640, 480, 0.7}`，探测 / 基线 / 上传帧全部走同一函数，结构上不可能不一致 |
| 5 | 成功冷却 6 秒；失败递增退避；无脸即重置 | `CaptureView.handleState()` + `startProbe()` | 成功 `cooldownUntil = now+6000`；失败 `min(6000, 1800+900×n)`；探测判定「镜头前没有人」持续 2.5s 就把 `attempts` 归零 |
| 6 | 重建下拉时屏蔽自身触发的 change | `useCamera.switchDevice()` 的 `selfSwitch` 标志 | 程序内切换置位，`setTimeout(…, 0)` 异步复位；UI 用 ActionSheet 而非原生 `<select>`，从根上减少误发 |

补充：§7.4.2 的「连续两次探测都通过才拉起验证」在 `probe()` 里用 `stableStreak >= 2` 实现；
§7.4.3 的「关闭/刷新要 `track.stop()`」在 `onBeforeUnmount` + `close()` 双保险。

## 3. 采集时序（顺序是死的）

```
IDLE → REQUESTING → READY → BASELINE → CAPTURING → SUBMITTING → DONE / ERROR
```

1. **BASELINE**：静默抓 1 帧（此时屏幕上**不出现任何指令**），
   `POST /face-api/challenge/start { baselineFrame, deviceHash }`；
2. 响应回来后**同一个同步块**里做两件事：把 `instruction` 写进响应式状态、立刻 `tick()` 采首帧。
   两者之间没有任何 `await` —— 这是「指令渲染与首帧采集是同一动作」的实现方式；
3. **CAPTURING**：`setTimeout` 固定 250ms 一帧（4fps），帧入队后**串行**上传；
   队列上限 4，超过丢最旧一帧并累加 `droppedFrames`（大屏/调试页会显示）；
4. 窗口到期（`windowMs`）或 `progress >= 1` → `POST /finish`；
5. `FA-4002`（多脸）→ 立即清队列、`track.stop()`、整屏阻断。

为什么不用「上一帧返回再采下一帧」：那样实际帧率被 RTT 拖到 2~3fps，
2 秒窗口只剩 5~6 帧，服务端 `MIN_FRAMES=8` 永远达不到，动作判据直接失效。
