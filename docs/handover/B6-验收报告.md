### 2.1 nginx 层 14 项（单点入口验收）

单点端口映射、HTTP→HTTPS 301、/healthz、HSTS/nosniff/referrer、/agent/ 去 X-Frame-Options、
gzip（text/html）、TLS1.2 可用 / TLS1.1 拒绝、**WS 经 nginx 握手 101 且首帧 `EVT_CONNECTED`**、
坏 token 握手放行后服务端断开（鉴权后置语义）、9MB 上传被 413（`client_max_body_size 8m`）、
连打触发 429 限流（10r/s burst 20）。

### 2.2 压测口径与结论

30 并发 = 10 场会话 × 3 名学生，每条流水走完整链路
（扫码 join → 挑战 start → 8 帧上传 → finish 三道门禁 → 落库）。

```
{"concurrency": 30, "wallSeconds": 245.9, "success": 30, "failed": 0,
 "errorRate": 0.0, "p50ms": 240397.9, "p95ms": 245848.9, "maxMs": 245864.5,
 "throughputPerSec": 0.12, "sampleFailures": []}
```

落库核验：`attendance` 68 行 / 68 个唯一 (session, student) 对，**零重复、零死锁**——
这正是文档 §15.2 对压测的核心断言（"30 并发 commit，无死锁、无重复记录"）。

两个验收口径（与 18 场景的两阶段同因——CASIA 合成帧活体分只有 0.02~0.10）：
1. **活体阈值 0**（阶段 A 口径）：合成帧过不了生产阈值 0.55，门禁语义由场景 07 在
   生产阈值下单独覆盖；压测关注的是 commit 落库层的并发正确性。
2. **挑战 TTL 600s**（默认 60）：单机 CPU 2 worker 撑不住 30 路同时推理（每条 ~8s CPU），
   finish 排队 100~245s，排队超过 60s 的挑战会被判过期。这正是文档 R3 登记的容量风险。
   生产默认 60s 不变；TTL 已参数化（`FA_CHALLENGE_TTL_SEC`）供部署时按容量调整。

**P50 240s 是排队等待，不是单条处理时间**：face 推理吞吐 2 worker ≈ 0.12 条/s（每条
~8s CPU），30 条流水串行消化 4 分钟。生产按 R3 复测（4 worker / GPU / 按到达率摊平）。

### 2.3 覆盖率口径

文档 15.2 未设硬性数字门槛（模板占位 `xx%` 未填），报告实测值：
CI `report-aggregate`（ITs 跑在 fa-bootstrap 进程里，单模块报告会严重低估，以聚合为准）
合计指令 47.5% / 分支 28.3% / 行 51.0%；fa-common（公共组件）指令 56.0%。
低值集中在 fa-org/fa-auth/fa-agent 的薄控制器层（单测不 mock 全链路，靠 18 场景 E2E 补足）。

## 3. 本轮修掉的真实缺陷

### 3.1 业务代码（B5 遗留 / B6 暴露）

| # | 缺陷 | 修复 |
|---|---|---|
| 1 | **大屏 WS 从未连通**：`SecurityConfig` 把 `/admin/sessions/*/live` 拦在 `authenticated()`，浏览器无法带 Authorization 头 | 放行 GET 该路径，鉴权由 `LiveWsConfig.authorized()`（验签+角色+黑名单）后置完成 |
| 2 | **移动端 join 不校验二维码**：`qrToken` 参数没有 `@Valid` 也没有 `qr.verify`，伪造/过期码也能进挑战 | 补 `JoinReq` 校验 + FA-3002 |
| 3 | **学生端班级/课程名恒 null**：`jdbc.queryForObject` 误用 RowMapper lambda | 改 `jdbc.query`（ResultSetExtractor 语义） |
| 4 | **申诉创建无实时推送**：大屏不知道有人申诉 | `AppealService` afterCommit 推 `EVT_APPEAL_CREATED` |
| 5 | **审计只有一句 detail**：申诉处理无前后状态 | `AuditWriter.write(before, after)` 摘要 |
| 6 | **基线污染误拒**：基线帧已张嘴 → 动作计数器基线虚高，正常张嘴被判 0 次（FA-4003） | `MouthActionCounter` 基线自愈（只回卷一次防递归） |
| 7 | **动作提示泄漏**：`FA_ALLOW_ACTION_HINT=1` 时任意动作可被客户端指定 | CR-010 `_pick_action` 白名单；生产默认关闭 |
| 8 | **移动端人脸建档无入口** | `POST /mobile/face/enroll` 写 PENDING_REVIEW + face_vector |
| 9 | **引擎懒加载无锁**：多线程首次并发 `load_all()` 互相覆盖，部分调用方拿到 None；且"加载到一半失败"会让 `_registry` 半赋值、永久跳过加载 | 双检锁 + 加载完才赋全局变量 |
| 10 | **挑战 TTL 硬编码**：`ttl_sec: int = 60` 写死，部署无法按推理容量调整（压测 30 路并发 finish 排队超 60s 即被判过期）；且 `_get` 约定带 `FA_` 前缀，首版环境变量没带上，改了两轮才生效 | `FA_CHALLENGE_TTL_SEC` 可配，默认 60 = 契约值 |

### 3.2 验收工具（本次发现，不影响业务）

| # | 缺陷 | 修复 |
|---|---|---|
| 11 | `verify-coldstart.sh`/`wait-healthy.sh` 用 `declare -A`，macOS 自带 bash 3.2 直接报错 | 改动态变量名（bash 3.2 兼容）；`wait-healthy.sh` 顺带清掉残留的 `minio` |
| 12 | `verify-nginx.sh` 用 curl 测 WS——curl 默认走 h2 会丢弃 Upgrade/Connection 逐跳头，握手必 400 | 改标准库 socket 发真 HTTP/1.1 握手；断言改为符合 Java 实际语义（101 + EVT_CONNECTED / 坏 token 断开） |
| 13 | 四个运维脚本存在 `$var（全角…` 写法，bash 3.2 会把全角首字节吞进变量名 → unbound | 全部改 `${var}` |
| 14 | `gzip_min_length 1024` 大于 SPA index.html（几百字节），gzip 对入口页不生效 | 调低到 256 |
| 15 | 压测脚本引用已重构掉的 `conftest.pick_persons`；帧序列只造一段张嘴，随机到 `MOUTH_TWICE` 必拒 | 改用 `candidates()` + 默认两段 opens |
| 16 | `_mouth_detectable` 预检未先加载引擎，`detector()` 返回 None 的 AttributeError 被 `except: return True` 吞掉，预检形同虚设 | 先 `synth._engine()` 再预检 |
| 17 | **容器跑的是旧镜像代码**：源码改动（config/engine）不 `compose build` 就不会进 face 容器，排查 TTL 时被"env 已是 600 但行为仍是 60"误导多轮 | 流程教训：改源码后必须 build；已在 MONITOR 取证后定位 |

## 4. 与文档的差异（需业主追认）

1. **服务数 6 而非 7**：MinIO 暂不入编排（原图归档未接线），定义保留在 compose 注释。
2. **`face_ro` 库级 SELECT**：初始化时序限制，收窄到表级列入遗留。
3. **CR-010 动作提示**：`FA_ALLOW_ACTION_HINT` 仅验收环境开启。
4. **大屏 WS 鉴权后置**：握手放行 + 连接后校验（JWT 只能走 query，契约如此）。

## 5. 未完成 / 风险

1. **人脸真机指标**：18 场景用 CASIA 合成帧；真机照片攻击拒绝率、误拒率需真机复测（WP-06 报告）。
2. **LLM Key**：Agent L2/L3 的 LLM 编排在拿到 Key 前用规则引擎兜底。
3. **`vite preview` 下移动端 WS 404**：仅 dev/preview 场景，容器内 nginx 路径正确。
4. **覆盖率没有 CI 硬门禁**：CI 只打印不卡门，建议 v1.1 补 threshold 检查。
5. **备份无异地副本**：本地 7 天轮转 + cron + 异地同步列入部署清单。
6. **压测结论只对本机配置成立**。
