## 0. 为什么 B5 先补 Java 模块

`internal.yaml` 冻结了三个 Agent 内部端点，但 `grep -ril agent backend-java` 只命中
auth 与错误码 —— **Java 侧一行未实现**。而 §11.5 要求「确认令牌由服务端签发」，
没有服务端就没有令牌，写操作闭环无从谈起。故本工作包拆成两半：

| 半 | 职责 | 关键约束 |
|---|---|---|
| `fa-agent`（Java） | 令牌签发与校验、工具执行、留痕、撤销 | **只有它能写业务数据**（单一写入口） |
| `agent-service`（Python） | 意图识别、编排、对话、确认卡 | **不碰数据库**，只调 Java 内部端点 |

## 3. 三个易错点（都真实踩过）

### 3.1 幂等键必须在消费令牌**之前**查

断点重放（网络抖动后用户再点一次「执行」）会带着**同一个令牌**回来。
如果在 `consume()` 之后才查幂等缓存，令牌已被 `GETDEL` 掉，第二次必然 FA-6002 ——
用户看到的是「令牌已过期」，而实际那次写操作**已经成功**了，于是他会重试第三次。

正确顺序：`toolCallId` 命中缓存 → 直接回上次结果 → 否则才 `consume()`。

### 3.2 `paramsHash` 必须对键顺序不敏感

预览时模型给的 params 与确认时回传的 params 可能键序不同（JSON 反序列化不稳定）。
直接 `toString()` 会得到不同哈希 → 误判「参数已变更」。
实现：`canonical()` 递归按键名排序后序列化，再 SHA-256。
`ConfirmTokenServiceTest` 用一个键序打乱的嵌套 Map 锁住了这个行为。

### 3.3 数字不许模型复述

`answer.py` 的 `_compose()` 先按工具结果生成**事实骨架**（含精确数字、单位、口径），
模型只做 `_polish()`（润色措辞）。若让模型"总结"数字，40 人会变 41 人，
而这类错误在审计日志里查不出来。

## 4. 实测

```
mvn -o -pl fa-agent -am test        → 8 tests, 0 failures（ParamsTest 4 / ConfirmTokenServiceTest 4）
python3 -m pytest tests -q -s       → 13 passed（test_graph 8 / test_tools 5）
mvn -o -T1C compile                 → 全量通过
```

`test_graph.py` 覆盖的 8 条：

1. 查询类问题走工具并带引用；
2. 闲聊不调工具（也不消耗模型额度）；
3. 提示注入被 intake 拦住；
4. 写操作只回预览、**不执行**；
5. 用户在确认卡点「取消」→ 不执行；
6. 点「确认」→ 令牌原样回传、只执行一次；
7. FA-6004 只调一次（不重试，避免越权试探打穿日志）；
8. FA-6002 文案为「确认令牌已过期，请重新发起」。
