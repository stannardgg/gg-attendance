### 密钥扫描实测

Gate 要求「故意提交一个假 `AWS_SECRET` → CI 的 gitleaks 必须失败」。实测发现这件事有**两道**防线，且第一道比预期的更靠前：

**测试一：AWS 格式令牌（第一次尝试用官档示例值）**

```bash
$ cat leak-test.txt
aws_access_key_id = AKIAIOSFODNN7EXAMPLE
aws_secret_access_key = wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY

$ gh pr checks 1
gitleaks 密钥扫描	pass	10s	    # ← 没拦住
```

原因：`AKIAIOSFODNN7EXAMPLE` 是 AWS 官方文档里的示例值，在 gitleaks 默认配置的 allowlist 内。
**这条同时说明：用官档示例值做密钥扫描测试是无效测试**，会得到一个假的「已通过」。

**测试二：随机格式的 AWS 密钥**

```bash
$ git push origin test/gitleaks-verify
remote: error: GH013: Repository rule violations found for refs/heads/test/gitleaks-verify.
remote: - GITHUB PUSH PROTECTION
remote:   - Push cannot contain secrets
remote:   —— Amazon AWS Access Key ID —— path: leak-test.txt:1
remote:   —— Amazon AWS Secret Access Key —— path: leak-test.txt:2
error: failed to push some refs
```

推送阶段即被 GitHub 服务端拒绝，**密钥根本没机会进入仓库**。这比「CI 失败」更早、更强。

**测试三：通用高熵密钥（Push Protection 覆盖不到的形态）**

```bash
$ cat leak-test.txt      # 值已脱敏，原文见下「一个真实踩坑」
DB_PASSWORD=<40 字符高熵串>
api_secret = "<64 字符高熵串>"

$ gh pr checks 1
gitleaks 密钥扫描	fail	9s	# ← 第二道防线生效
仓库卫生	pass	4s
检测技术栈	pass	5s
```

**结论**：两层防线均有效——Push Protection 拦已知格式，CI gitleaks 兜通用高熵值。测试分支 `test/gitleaks-verify` 与 PR #1 已删除，`main` 未被污染。

#### 一个真实踩坑：写文档时把测试密钥原文贴了进去

第一次提交这份交接记录后，`main` 的 Secret Scan **失败了**，命中的是本文档的第 94、95 行——我在里面贴了测试用的假密钥原文，想「留个证据」。

```
RuleID:  generic-api-key
File:    docs/handover/WP-00.md
Line:    94, 95
```

教训有两条，都值得记下来：

1. **gitleaks 扫的是全历史、全文件类型，包括 Markdown**。不存在「写在文档里就安全」这种事。
2. **测试密钥的取证要脱敏**：写「用了什么形态的密钥」「哪条规则命中」「job 结论」，但不写密钥值本身。证据的效力来自可复现的步骤，不来自原文。

处理方式：改写本文档 → 用 `commit --amend` 把密钥从这条提交里去掉 → 强推 `main` → 重打 `batch-0-done`。
之所以能 amend 而不是必须 `filter-repo`，是因为这条提交是 `main` 的最新一条、且没有被其他人拉走。**如果已经过去几天、有人基于它开了分支，就必须走 §19.7 的轮换 + 历史清理流程。**
