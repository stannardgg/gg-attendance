# CR-008 · 移动端「探测」没有服务端接口，人脸尺寸只能由服务端判

- 提出人：WP-11（移动端前端）
- 提出日期：2026-11-19
- 状态：**已按本地探测落地，待确认**
- 阻塞范围：无（先落地，再决定是否补接口）
- 严重度：低

## 1. 问题

§7.4.1 第 4 条要求「探测帧与校验帧必须用同一降采样参数」，§7.4.2 第 1 条要求
「连续两次探测都返回『可开始』才拉起验证」。这两条都在讲**探测**，
但 `face-api.yaml` 里没有任何探测端点：

- `challenge/start` 会真的创建挑战（写 Redis、绑设备、返回动作），不适合当探测；
- `challenge/{id}/frame` 需要已存在的 challengeId；
- `health` 与探测无关。

而「太远」这个判断需要**人脸框宽度**，那必须跑 SCRFD 检测 —— 移动端没有本地模型。

## 2. 已落地的折中

`mobile-web/src/features/checkin/composables/useCamera.ts`：

- 探测 = **本地轻量判断**：亮度均值（45~225）、缩略图方差（>12，判断"镜头前到底有没有东西"）、
  相邻帧亮度差（<6 判稳定），**连续两次通过**才自动拉起 `challenge/start`；
- 探测帧与基线帧、上传帧全部走**同一个 `captureSmall()`**，
  参数只有一份常量 `CAPTURE = {640, 480, 0.7}`，物理上不可能出现"两处参数不一致"；
- 「太远 / 太小」不本地判：由服务端在 `finish` 时按身份一致性门禁给出 `FA-4007`，
  学生在结果页看到的是「身份校验未通过，请本人操作」+ 具体建议。

也就是说：**§7.4.1 #4 的成因（两处参数不同）被结构性地消除了**，
但 §7.4.2 #1 的"探测"语义弱化为「画面可用性探测」，不是「人脸可用性探测」。

## 3. 建议

若要严格实现"探测说太远就提前拦"，需要一个**无状态**的探测端点：

```yaml
/face-api/probe:
  post:
    summary: 单帧可用性探测（不创建挑战、不写状态）
    requestBody: multipart { frame }
    responses:
      '200':
        data: { faceCount, faceWidth, brightness, sharpness, ready: boolean, hint: string }
```

前端可每 400ms 调一次（单帧 ~35KB，4fps 上行对教室 WiFi 是负担，建议 2fps）。

**权衡**：增加上行流量换更早的失败反馈。
当前"本地探测 + 服务端一次判定"的方案在真机上耗时可接受（一次挑战 3 秒），
建议**先不补**，等 B6 真机联调后再定。
