# CR-014 · 建档案时做同脸查重（一人一档）

- 提出人：主人（2026-11-21 会话内指示「建档时做同脸查重」）
- 提出日期：2026-11-21
- 状态：✅ **已批准并实现**
- 关联：§4.1 D5 / §5.4 采集门限 / §6.3 错误码 / §10.2 比对规则 / §13.4 信息边界
- 影响工作包：WP-07（Java 人脸域）、WP-11（移动端）、WP-13（E2E）

## 1. 问题

2026-11-21 19:13 现场：学生 158「测试」采集完成后立刻签到，连续两次返回
「签到未通过 · 人脸不匹配」（`FA-4005`）。排查结论：

1. 活体、首末帧身份一致性、动作次数三道门禁**全部通过**，只有 1:N 比对没过；
2. 向量索引健康（536 条 / 107 名学生，158 的 5 条样本在位且自洽 0.779~0.923）；
3. 全库 5565 个跨身份配对里，相似度 ≥ 0.5 的**只有一对**：学号 57「瓜葛」与
   158「测试」= **0.692**——同一张脸被录进了两个学号，且两人同班、同一场次的应到名单；
4. 比对门的判据是 `top1 >= 0.45` **且** `top1 - top2 >= 0.06`。两个档案同脸时比分
   必然咬在一起，余量掉到 0.06 以下 → 判「像两个人」→ 本人被拒签。

根因是**建档环节没有任何跨学生约束**：`FaceEnrollService.enroll` 只校验
「本人是否已提交/已通过」，同一张脸可以无限次录进不同学号。余量规则本是防冒名的
设计（§10.2），在双档场景下反而误伤本人；这不是阈值问题，调阈值只会把误伤换成放行。

## 2. 方案

### 2.1 落点与时机

`POST /api/v1/mobile/face/enroll`（`FaceEnrollService.enroll`），在**读完 Redis 样本之后、
写任何数据之前**：

```
读 5~10 张样本向量 → 同脸查重 → 写同意时间戳 → 整批替换 face_vector → 置 PENDING_REVIEW
                      └─ 命中即抛 FA-4008，后面三步一步都不执行
```

放在这个位置而不是审核环节：审核人看到的只有样本图，判断不了「这张脸是否已被另一个
学号占用」；等审核时才发现，样本已经躺在库里了。

### 2.2 判据

| 项 | 约定 |
|---|---|
| 相似度 | 余弦（入库向量与样本均已归一化，等价于点积；实现里仍双侧归一化，不假设上游） |
| 比对范围 | `student.status = 'ACTIVE'` 且 `face_profile.status IN ('ACTIVE','PENDING_REVIEW')` 的**他人**向量 |
| 聚合 | 跨候选 × 跨样本取**最大值**，不做平均——平均会被同一人的其余角度稀释 |
| 阈值 | `DUP_FACE_SIM`，默认 **0.55**（`FA_DUP_FACE_SIM` 可覆盖） |
| 命中 | 抛 `FA-4008`（HTTP 409），文案「这张人脸已用于其他学生档案」 |

排除三类行：

- **本人**：驳回重采时旧向量要到落库那一步才整批删除，不排除会自己撞自己；
- **非 ACTIVE 学生**：归档/删除的人不该继续占着这张脸；
- **REJECTED 档案**：废样（模糊、非本人）拦人会让人永久无法重采，比漏放更糟。

### 2.3 阈值取值依据

2026-11-21 实测（107 名学生 / 536 条向量 / 5565 个跨身份配对）：

| 统计量 | 值 |
|---|---|
| 不同人最高相似度 | 0.431 |
| p99.9 | 0.389 |
| p99 | 0.317 |
| 中位数 | 0.113 |
| 同脸异档（57/158） | 0.692 |

取 0.55：与不同人实测上限留 0.12 余量，同时能抓住 0.6 以上的同脸。查重是兜底而非门禁，
宁可漏掉「同人换光后掉到 0.5~0.55」的边缘，也不要拦错人——误拦的代价是学生当天无法
建档、无法签到。

### 2.4 为什么不在 face 服务算

- face 的内存索引只有 `ACTIVE` 学生（CR-002 快照口径），而两份待审核档案一条都不在索引里；
- 索引是 10~60 秒轮询的快照，刚落库的档案在窗口内查不到，靠它查重会漏；
- 向量本来就由 Java 解密（`VectorCrypto` 是解密边界），点积是纯算术，不值得再引入
  一次跨服务调用和一份新的接口契约。

代价是每次提交采集多一次全表读 + 解密（当前 536 行 / 约 1MB，毫秒级；千级学生仍无感）。
`face_vector` 目前没有按学生分组的索引以外的高效过滤，规模上万后再考虑把「查重专用
索引」常驻内存。

### 2.5 信息边界

`FA-4008` 的响应只有文案，**不返回**对方学号、姓名或相似度原值；审计同样不写相似度
（§13.4 禁止）。冲突对象与相似度只进服务端 WARN 日志，供运维排查。

## 3. 已知限制

1. **并发建档**：两个学生同时提交、且都在对方尚未落库的窗口内通过查重，理论上仍可
   双档。概率极低（需要同脸两人在同一秒级窗口提交），且需要人工介入才能构造；
   彻底解法是把查重做进同一个串行点（如按人脸分桶加锁），当前不做。
2. **审核不复检**：查重只在提交时做一次。若审核期间另一份同脸档案先通过，不会回扫。
   需要时可在审核通过后跑一次全库扫重（管理端工具），当前不做。
3. **阈值边缘**：同一个人换光照/角度后相似度可能落到 0.5~0.55，这类会漏。这是有意的
   取舍（见 2.3），不是缺陷。

## 5. 验证

- 单测（`FaceDuplicateCheckerTest`，8 例）：同脸命中、不同人不拦、阈值边界、多探针取最大、
  多候选取最高、维度不符跳过、坏字节放行、余弦归一化。`mvn -pl fa-org -am test` 全绿。
- 契约一致性测试（`ErrorCodeContractTest`）5 例通过，错误码数量与契约对齐。
- 实测口径复核：用线上向量库算 5565 个跨身份配对，0.55 阈值下除已知同脸对外**零误伤**。
