# CR-001 · 应到名单「会话期间固定」缺少承载表

- 提出人：WP-01（B1 契约冻结）
- 提出日期：2026-11-19
- 状态：**待裁决**
- 阻塞范围：WP-04（会话关闭补 ABSENT）、WP-13（场景 5、15）
- 严重度：中（不阻塞 B1 交付，但 B4 开工前必须定）

## 1. 问题

§4.2 明确要求：

> 会话的**应到名单**在创建时确定：`students WHERE class_id = session.class_id AND status = 'ACTIVE'`……
> **名单在会话存续期间固定，中途转入/转出的学生不影响本场。**

但 §5.2 的 15 张表里没有任何一张能承载这份"固定名单"：

- `attendance` 在会话创建时**没有行**（§4.3：记录只在 commit / 关闭 / 手动调整时产生）；
- `student.class_id` 是**当前**归属，会被转班改写；
- `checkin_session` 只存 `class_id`，不存成员快照。

也就是说：会话创建后，服务端无法知道"创建那一刻班上都有谁"。

## 2. 影响面（具体会错在哪）

| 场景 | 期望（§4.2） | 无快照表的实际行为 |
|---|---|---|
| 学生 A 在签到进行中转出本班 | 本场仍应记 A 为 `ABSENT` | 关闭时按当前 `class_id` 查，A 被漏掉，本场没有他的记录 |
| 学生 B 在签到进行中转入本班 | 本场不该出现 B | 关闭时 B 被补 `ABSENT`，**误伤**（B 根本没被通知签到） |
| 学生 C 会话期间 `status` 改为 `ARCHIVED` | 本场仍应记 `ABSENT` | 同上，漏记录 |
| 应到人数展示 | 创建时快照 | 大屏刷新时会变（人数漂移） |

概率：都发生在 10 分钟窗口内转班，实际很低。但**误伤（B 场景）会产生学生投诉，且考勤记录是申诉的证据链起点**。

## 3. 三个方案的取舍

### 方案 A：新增 `session_roster` 表（严格满足 §4.2）

```sql
CREATE TABLE session_roster (
  id         BIGINT NOT NULL AUTO_INCREMENT,
  session_id BIGINT NOT NULL,
  student_id BIGINT NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_sr (session_id, student_id)
);
```

- 创建会话时把班级全体 `ACTIVE` 学生批量插入；关闭时以本表为唯一依据补 `ABSENT`。
- **代价**：表清单从 15 变 16，属契约变更；每场签到多 40 行写入（可忽略）。
- **收益**：语义完全正确，"应到/实到"不再依赖写入时刻的班级状态。

### 方案 B：按关闭时的班级成员计算（零结构变更）

- 关闭时 `INSERT ... SELECT` 当前 `class_id + status='ACTIVE'` 的学生。
- **代价**：上面表格里的三种偏差都保留；§4.2 的措辞需要改。
- **收益**：不改契约，不改 DDL，实现最简单。

### 方案 C：创建会话时预写 `ABSENT` 行（已否决）

- 让"名单固定"落在 `attendance` 上，创建时全体预写 `ABSENT`，签到成功再改 `PRESENT`。
- **否决理由**：破坏"实时进度"语义——学生还没扫码，大屏就显示"全员缺勤"，
  教师无法判断谁真的没来。而且 `reject_gate` 等字段在预写行里没有意义。

## 4. 建议

**推荐方案 B**，理由：

1. 偏差只在"会话期间转班"时出现，而转班本身是低频管理动作且**必定留下审计记录**
   （§5.3.1：转班 = 改 `class_id` + 留审计），事后追溯有据可查；
2. v2.0 的定位是"能用的课堂签到"，不值得为 10 分钟窗口内的转班引入第 16 张表和一套新写入路径；
3. 若将来真要做严格快照，方案 A 可以随时以 `V2__alter_session_roster.sql` 增量加上，**不构成不可逆决策**。

同时建议**把 §4.2 的措辞改为**：

> 应到名单 = 该班级当前在读学生。名单在会话存续期间**按实时班级成员计算**；
> 会话期间发生的转班以审计记录为准，不回溯调整已关闭场次的考勤。

若坚持原文"固定"，则必须走方案 A，并在 §5.2 表清单补第 16 行。
