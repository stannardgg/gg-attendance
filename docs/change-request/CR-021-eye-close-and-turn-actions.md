# CR-021 · 新增闭眼与左右转头动作

- 提出人：主人（2026-11-22 会话内指示「增加眨眼和左右转头动作」）
- 提出日期：2026-11-22
- 状态：✅ **已批准并实现**
- 关联：§4.4.1 动作库 / §4.4.3 挑战规则 / §10.5 配置项 / §16.3 验收场景
- 影响工作包：WP-06（Python 活体与动作）、WP-11（移动端文案）、WP-13（E2E）

## 1. 动机

CR-018 把嘴部动作整体停用后，动作库只剩「靠近 / 离远」两个，都是**位移**类：
一段"举着手机靠近"的预录视频命中概率 1/2。本 CR 补两类与位移无关的动作，
把随机维度从 2 扩到 5：

| 动作 | 判据信号 | 与位移的关系 |
|---|---|---|
| `EYE_CLOSE` | 眼框暗像素占比下降 | 正交（原地不动也能做） |
| `TURN_LEFT` / `TURN_RIGHT` | 5 点偏航代理 | 正交（尺度不变） |

**为什么是「闭眼」而不是「眨眼」**：§7.1 固定 4fps（250ms/帧），一次自然眨眼
只有 100~300ms，多数眨眼完整落在两帧之间；再要求「连续 ≥2 帧达标」时，
**真人做对也判不过**。这不是阈值问题，是采样定理问题（v2.0 已登记）。
改为「闭眼约 1 秒再睁开」后，同一套眼区判据在 4fps 下能稳定拿到 2~4 帧，
交互意图不变（都是眼睑闭合），但不再赌采样运气。契约里的 `BLINK` 仍留在
`disabled`，理由改写为「由 EYE_CLOSE 取代」。

## 2. 方案

### 2.1 闭眼判据：眼框暗像素占比下降

眼睑盖住虹膜 → 眼框里的暗像素**减少**，与张嘴（暗像素增多）同构、方向相反。
计数器 `EyeCloseCounter` 复用「连续段 + 基线相对」的结构，并保留与
`MouthActionCounter` 对称的**基线自愈**：基线帧若正好拍在闭眼上，用序列里
观测到的最高值（睁眼）重算一次。

眼框定位用 **106 点的眼球轮廓**（`EYE_LM_LEFT = 33~42`、`EYE_LM_RIGHT = 87~96`，
本机 20 个身份实测反推，与 `mouth_rect` 同一套做法），关键点只做定位。
不用「5 点眼位 + 固定倍率框」的原因是实测更差：头部侧倾时 5 点有偏，
框会落到眉毛上，80 个身份里 4 例闭眼降幅归零；换轮廓后 78/80 达标。
关键点模型不可用时（首帧锁不上）退回 `eye_rects_from_kps`，保证动作仍能出。

### 2.2 转头判据：SCRFD 5 点偏航代理

```
yaw_proxy = (鼻尖 - 双眼中点) · (右眼 - 左眼) / |右眼 - 左眼| / 瞳距
```

为什么不违反 v2.0 的「关键点不能做判据」：禁的是 `2d106det` **形状回归器**
（强整体形状先验，偏 20° 眼部指标只变 0.03~0.05）；这里的 5 点来自 **SCRFD 检测头**，
直接回归原图坐标，姿态没有被归一化掉。

- **沿眼轴投影**而不是直接取 x 差：歪头（滚转）的位移被投影消掉，实测残余
  来自检测器自身在侧倾下的关键点偏差（±15/±30° 漂移 mean 0.030 / max 0.108）。
- **方向相对基线判定**，不用「序列最大/最小」：否则「先左后右」同时满足两个方向。
- **符号**：`kps[0]` 是图像左侧的眼睛（60/60 身份成立）。代理增大 = 鼻尖偏向画面
  右侧 = 对着镜头的人把头转向**他自己的左边**，所以 `TURN_LEFT` 对应代理增大。
  这依赖「上传帧未镜像」——前端只在 `<video>` 上做 CSS 镜像，`drawImage` 取原始流。

### 2.3 可做性门槛（不满足就退出抽签，而不是判学生失败）

| 动作 | 门槛 | 不设的话 |
|---|---|---|
| `EYE_CLOSE` | 基线眼区暗度 ≥ 0.10 且瞳距 ≥ 45px | 浓妆/逆光/人太远时没有下降空间，照做也判不过 |
| `TURN_*` | \|基线代理\| ≤ 0.10 且人脸左右各留 4% 画面 | 已经偏头再往同侧转会滑出检测范围；贴边转头会出框 |

所有候选都不合格时（极端构图）退回全量白名单并打 WARN 日志：与其当场拒绝签到，
不如让学生试一次，失败还有申诉这条路。

### 2.4 转头动作的连带修正：用「最正脸」那一帧做 1:N

`finish` 的 match 门禁用 `last_emb`。转头动作的末帧可能是侧脸，拿侧脸特征做 1:N
会让 similarity 掉下去，冒出一个与动作无关的 `FA-4002`——判据在惩罚正确行为。
因此每帧记下「离基线偏航最近」的那一帧特征（`frontal_emb`），`finish` 时若
动作是 `TURN_*` 就用它替换 `last_emb`（身份一致性门禁同样受益）。

## 4. 验证

### 4.1 判据分离度（`probe_action.py --eye` / `--pose`，本机 CASIA 合成）

| 判据 | 信号 | 噪声（抖动±4px + JPEG q60 + 亮度±5%） | 分离度 |
|---|---|---|---|
| 闭眼 | 睁眼 0.281 → 闭眼 0.103，逐人降幅 **0.178 ± 0.065** | std **0.0152** | 0.06 / 0.0152 = **3.9σ** |
| 转头 | 基线代理 −0.042 ± 0.035（跨身份，判据用本人基线） | std **0.0104** | 0.12 / 0.0104 = **11.5σ** |

- 闭眼：75/80 达标；未达标的 5 例里 1 例基线只有 0.048（被 `eye_base_min=0.10`
  挡在抽签外），其余集中在低对比/弱光样本。
- **上传口径要单独量**（`--eye --wire`，把素材过一遍 JPEG q90）：服务端看到的就是
  压缩帧，降幅普遍比原始帧小 0.01~0.02。80 个身份里原始帧判不出的 3 个（010/017/051），
  上传口径变成 7 个（多出 024/026/060/070）——**这 4 个不是系统缺陷，是合成素材在
  压缩后不够**。E2E 的身份预检因此必须按上传口径筛（见 4.3）。
- 转头：滚转 ±15/±30° 漂移 mean|Δ|=0.030、max=0.108，阈值 0.12 刚好留出余量。
- **梯度能量判据已否决**：闭眼后眼框 Sobel 幅值相对降幅仅 4.8%，且 20% 身份反号。

### 4.2 自动化

- 新增用例：闭眼计数/需 2 帧/基线自愈、转头方向互斥、转头门禁正负例、闭眼门禁、

- 契约语法校验通过（`json.load` + `yaml.safe_load`）；`mobile-web` 的 `vue-tsc` 通过。

### 4.3 容器与 E2E

- 重建 face 镜像后容器内冒烟：抽样只出 5 个动作、`action_hint` 对三类动作生效；
  `BLINK` 报「动作已停用」（不是「未知动作码」——契约里写了它被 EYE_CLOSE 取代，
  联调时应该看到原因）。
- E2E：新增场景 19（闭眼判通过）、20（要求闭眼但一直睁眼 → `FA-4003` 0/1）、
  21（要求转头但静止 → `FA-4003` 0/1）；回归场景 01/02/04/08/09/13/14。
  阶段 A 口径（`LIVENESS_THRESHOLD=0`，CASIA 静图活体分天花板）。

**补的坑：E2E 身份预检必须覆盖新动作**。场景 19 一开始是间歇性红：同一套代码，
抽到某个身份就过、抽到另一个就不过（实测 9 次里 3 次）。根因不在判据而在造帧——
`conftest.candidates()` 只筛"合成张嘴能不能判出来"，闭眼加入后没人管，而 CASIA
里确实有一批身份的「肤色覆盖眼睑」做不出 0.06 / 0.6 倍的降幅。

修法两处：① 预检改成按 `ACTION_WHITELIST` 决定筛哪几族（回滚张嘴族只需改 `.env`）；
② 预检**必须把画面过一遍 JPEG q90 传输编码**再量——服务端量的是压缩后的帧，
压缩会抹平肤色块与睫毛线，降幅普遍小 0.01~0.02，40 个身份里有 2 个是"原始帧刚好
过线、线上刚好不过"。补完后 40 个身份剔除 4 个（010/017/024/026），场景 19 连跑
6 次全绿。同理，判失败的逐帧数值也补了日志（`闭眼未计数` / `转头未计数`），
误拒申诉时能直接回答"差多少、哪一帧没跟上"。

## 5. 已知限制

1. **眨眼仍不可用**。`BLINK` 没有恢复，恢复的只是"眼睑闭合"这个交互——理由见 §1。
   想真正支持眨眼必须提高采集帧率（服务端单帧推理成本是瓶颈），不在本 CR 范围。
2. **歪头可能被算成转头**。滚转 ±30° 的代理漂移最大 0.108，逼近阈值 0.12，
   极端歪头在个别身份上会满足 `TURN_LEFT`。这是**单向**误放行（不会误拒，
   学生仍做了活的头部动作），代价可接受；要彻底分开需要再加 bbox 长宽比门禁。
3. **左右方向依赖未镜像**。若将来前端改成镜像采集（`drawImage` 前加 `scaleX(-1)`），
   `TURN_LEFT` / `TURN_RIGHT` 会整体反转，且是 100% 系统性错误。
   真机验收时必须先确认「按提示向左转，`yaws` 增大」。
4. **眼镜/浓妆削弱眼区信号**。眼框里混入镜框、眼线会同时抬高睁眼与闭眼基线，
   降幅变小。合成素材里没有稳定的眼镜样本，这一项完全留给真人复核。
5. **E2E 覆盖不了转头正例**。CASIA 是正面平面贴图，投影变换不会让鼻尖相对双眼
   位移（那是 3D 突出部才有的效应）。转头的正例只有计数器单测与 `--pose` 的
   噪声/滚转数据，**信号幅度完全依赖真人复核**。
6. **动作变多 ≠ 更强**。5 个动作意味着每个动作 1/5 概率；对预录视频的约束来自
   「不知道会被要求哪一个」，一旦某个动作被拍成素材就能复用。
   真正的主防线仍是活体与首末帧身份一致性。

## 6. 回滚

```bash
# 1) 摘掉新动作（保留尺度两个）
ACTION_WHITELIST=MOVE_CLOSER,MOVE_AWAY

# 2) 必须重建容器：restart 不会重读 .env
DOCKER_BUILDKIT=0 docker compose up -d --force-recreate --no-deps face
```

判据代码与阈值保留，无需 revert；存量的 `attendance.action_seq` 里的 `EYE_CLOSE` /
`TURN_*` 仍可读（契约不写枚举）。
